# PDF Merge & Split — Conversion Audit

## Purpose

Audit the conversion readiness, product accuracy, regional positioning, merge and split clarity, page-control proof, preservation messaging, privacy, monetization transparency, and unsupported-claim risk of every localized Play Store listing for PDF Merge & Split (PMAS).

This audit verifies that every locale preserves the real product promise while adapting its conversion angle to the document needs that users in that region are most likely to recognize.

The shared product foundation is:

**Merge multiple compatible PDF documents in a chosen order, or split one PDF into new files using bookmarks, manual cut points, equal parts, or a maximum number of pages.**

Users can also:

* Reorder PDFs before merging
* Review how pages will be distributed
* Add an optional cover page to the result
* Save created PDF files
* Open results in compatible apps
* Share created files
* Rename or delete saved results in My PDFs
* Process PDF content locally on the device

The localized listings must not be literal translations of one global golden.

Each locale may change:

* the leading conversion angle
* the priority between merge and split
* the practical document examples
* the order of screenshots
* the number of screenshots
* the amount of technical explanation
* the vocabulary used for files, pages, parts, bookmarks, and documents
* the relative emphasis on privacy, control, simplicity, speed, preservation, or precision

Regional adaptation must not change the actual product scope.

---

## Global Product Identity

All locales must preserve the same product identity:

**PDF Merge & Split is a local PDF organization utility that creates new PDF files by combining complete documents or dividing one document at user-controlled page boundaries.**

It is not:

* a PDF reader
* a full PDF editor
* a scanner or camera-scanning app
* an OCR tool
* a PDF compressor
* a format converter
* a form editor
* a digital-signature tool
* a redaction tool
* a damaged-PDF repair app
* a password-removal utility
* a cloud processing service
* an AI document-analysis tool
* an automatic document-classification service
* a guarantee that every advanced PDF feature will survive rewriting unchanged

The listing should sell practical control over document organization, not abstract file manipulation.

---

## Global Conversion Standard

Every locale must communicate the following product truths, although the order and emphasis may vary by region:

1. The app works specifically with PDF files.
2. Users can merge multiple compatible PDFs into one result.
3. Users can control the source order before merging.
4. Users can split one compatible PDF using several methods.
5. Bookmark-based splitting uses bookmarks already present in the source PDF.
6. Manual cut points let users choose where new files begin.
7. Equal-parts splitting divides the document according to page count, not exact byte size.
8. Maximum-pages splitting limits the number of source pages assigned to each generated part.
9. The app creates new PDF result files.
10. An optional cover can be inserted as a real PDF page where supported.
11. Source PDFs are not presented as being destructively overwritten.
12. Original pages remain PDF pages rather than being intentionally rasterized into screenshots.
13. Created files can be saved, opened, shared, renamed, and deleted through the implemented flows.
14. PDF processing happens locally on the device.
15. No account is needed for PDF processing.
16. PDF content is not uploaded for merging or splitting.
17. Monetization remains secondary to the main utility.
18. No unsupported editing, OCR, compression, repair, security, signature, or universal-preservation claims are introduced.

The first visual impact should communicate one of these high-value relationships:

**Several PDFs → one organized PDF**

or:

**One PDF → several useful PDF files**

or, preferably when regional conversion permits:

**Merge or split PDFs according to your needs**

The listing must not open with:

* settings
* an empty My PDFs page
* a file picker without context
* a technical PDF-object screen
* an advertisement or upgrade screen
* a generic privacy statement without showing the core product
* a bookmark list that does not explain the resulting files
* a cover editor without explaining that the cover becomes part of a merge or split result
* an abstract file-management composition
* a scanner, printer, or cloud-drive visual that implies unsupported functionality

## Why PMAS Must Not Be Positioned Like EMAS

PMAS may reuse the interaction structure of EPUB Merge & Split, but the user problem is different.

EPUB users usually think in books, chapters, sections, reading applications, and cover identity.

PDF users more often think in:

* reports
* contracts
* school material
* invoices and receipts
* forms
* scanned documents
* manuals
* statements
* appendices
* page ranges
* files that are too long to send or review conveniently

Therefore, PMAS should not simply replace the word “EPUB” with “PDF.”

The PDF listing should lead with practical document outcomes:

* combine related documents into one file
* place PDFs in the correct order
* separate a long document into useful parts
* choose exact cut points by page
* use existing bookmarks when available
* create parts with a selected page limit
* keep the original files separate
* preserve real PDF pages without intentionally turning the document into images

The cover workflow is supportive, not central. For PMAS, a cover is best framed as a title page, divider, project cover, report cover, or visual identifier for the created PDF.

## Default Screenshot Strategy

The default global recommendation is a compact set of **6 screenshots**:

1. Main merge-or-split promise
2. Merge ordering and document organization
3. Split by bookmarks or manual cut points
4. Equal parts or maximum pages
5. Optional cover page and final review
6. Created files, My PDFs, open/share actions, and local processing

This is a default conversion structure, not a rigid localization rule.

A regional golden may use **5 screenshots** when:

* bookmarks and manual cut points can be explained together clearly
* equal parts and maximum pages can share one readable composition
* the market responds better to a shorter product story
* one function has significantly higher local search intent
* the available raw UI allows two related benefits to be shown without crowding

A regional golden may use **7 screenshots** only when:

* merge and split require separate proof
* the locale benefits from additional explanation
* bookmark splitting needs its own visual
* manual page boundaries need their own visual
* each additional screenshot communicates a genuinely distinct conversion benefit
* the sequence remains understandable at Play Store preview size

Do not add screenshots only to show every screen in the application.

## Core Conversion Hierarchy

The default hierarchy is:

**Main promise → page control → split method → output preview → result preparation → local ownership**

Regional variants may legitimately prioritize different paths.

### Merge-first hierarchy

Useful when searches around combining documents, reports, scans, receipts, contracts, or assignments are more valuable:

**Several documents → chosen order → one result → optional cover page → save and share**

### Split-first hierarchy

Useful when long-document handling, page extraction by ranges, study material, submission limits, or easier sharing are stronger motivations:

**Long PDF → choose split method → preview parts → create smaller PDF files → save locally**

### Precision-first hierarchy

Useful in markets that respond strongly to clear rules and predictable output:

**Choose page boundaries → verify ranges → create separate files → keep originals unchanged**

### Privacy-first supporting hierarchy

Useful in markets where uploading contracts, statements, forms, or personal records to a website creates distrust:

**Merge or split locally → no document uploads → control the result → save and share**

Privacy may strengthen the primary proposition, but it should not replace it.

## Merge-Scope Accuracy

Safe merge claims:

* Merge multiple PDFs into one document
* Combine PDF files in the order you choose
* Organize reports, scans, forms, or related documents before creating the result
* Keep different page sizes and orientations where supported by the PDF engine
* Create one new PDF from several source files
* Keep source PDFs available separately
* Add an optional cover page to the merged result
* Save, open, rename, delete, or share the merged result through the implemented actions
* Keep text and vector content as PDF content rather than intentionally converting every page into an image

Use carefully:

* Preserve every annotation
* Preserve every link
* Preserve every bookmark hierarchy
* Preserve forms
* Preserve digital signatures
* Preserve page labels
* Preserve attachments
* Preserve JavaScript actions
* Preserve every font exactly
* Merge encrypted or password-protected PDFs
* Merge unlimited PDFs
* Merge any number of pages
* Maintain perfect compatibility with every PDF viewer
* Preserve every metadata field

These claims require verification against:

* memory handling
* practical device limits
* malformed source PDF behavior
* encrypted-document handling
* annotation import
* external and internal link rewriting
* bookmark destination rewriting
* page-label reconstruction
* AcroForm reconstruction
* digital-signature invalidation
* attachment and portfolio handling
* embedded font behavior
* page rotation and crop boxes
* output validation

Avoid:

* Merge any document format
* Merge Word, Excel, images, or EPUB files into PDF unless a separate verified conversion flow exists
* Merge password-protected PDFs without entering a password
* Preserve every PDF exactly
* Keep digital signatures valid after rewriting
* Guaranteed compatibility with every viewer
* Automatically repair broken PDFs while merging
* Compress the result automatically
* Reduce file size without quality loss
* Edit the document text while merging

## Split-Scope Accuracy

Safe split claims:

* Split a PDF by existing bookmarks
* Split a PDF at page positions you choose
* Divide a PDF into a selected number of parts
* Split using a selected maximum number of pages per file
* Review which page ranges will be included
* Create several new PDF files
* Preserve the original PDF separately
* Insert an optional cover page at the beginning of each created part when that option is selected
* Keep original pages as PDF pages rather than intentionally rendering them into images

Use carefully:

* Equal parts
* Same-size parts
* Exact maximum pages
* Split by chapter
* Extract every section
* Split every PDF
* Preserve all bookmarks in every result
* Preserve all internal links across separate outputs
* Preserve interactive forms
* Keep digital signatures valid
* Create independent documents from every bookmark

“Equal parts” must reflect the actual algorithm.

For PMAS, it should mean:

* the source pages are distributed as evenly as possible across the selected number of output files

It must not be interpreted as:

* identical byte size
* identical visual complexity
* identical storage size
* identical number of images or annotations

“Maximum pages” must also reflect the implementation.

Safer wording includes:

* Split using a maximum number of pages per file
* Create parts based on the page limit you select
* Divide a long PDF into files with up to the selected number of source pages
* Organize the document into page-limited parts

When an optional cover page is added to every result, public copy should avoid ambiguity about whether the cover counts toward the selected source-page limit unless the implementation explicitly defines that behavior.

Avoid:

* Split by exact MB size
* Compress a PDF to meet an upload limit
* Guarantee identical file sizes
* Detect chapters using AI
* Extract text sections automatically
* Split by title, heading, or OCR content
* Repair invalid pages while splitting
* Preserve every cross-document link after separation

## Bookmark-Splitting Accuracy

Bookmark splitting depends on bookmarks already available in the source PDF.

The listing may explain this using accessible language:

* Use the bookmarks already included in your PDF
* Split according to the document’s existing bookmark structure
* Create parts from available document markers
* Review how bookmarked sections will be distributed
* Choose whether to use document boundaries, original bookmarks, or supported bookmark options during merge

Avoid implying that:

* every PDF contains bookmarks
* the app invents bookmarks when none exist
* bookmarks always represent chapters
* every bookmark creates a useful standalone file
* nested bookmark hierarchies are always preserved perfectly
* bookmark names are generated using AI
* the app understands the meaning of the document
* missing bookmarks are reconstructed automatically

Technical terms such as outline dictionary, destination array, named destination, or action object should not dominate public conversion copy.

When no bookmarks exist, PMAS must not be marketed as creating them automatically.

---

## Manual Split-Point Accuracy

Manual split points should be framed as visible page control.

Safe wording:

* Choose where each new PDF begins
* Add split points between pages
* Separate specific page ranges
* Review the resulting parts before creating them
* Decide exactly where the document is divided

Avoid wording that makes the feature look like:

* text editing
* page deletion
* page reordering
* OCR-based section detection
* arbitrary byte cutting
* extraction of non-contiguous pages unless that workflow exists

The clearest visual relationship is:

**Pages 1–8 → Part 1**  
**Pages 9–16 → Part 2**  
**Pages 17–24 → Part 3**

The ranges shown must match the real UI and preview behavior.

---

## Equal-Parts Accuracy

The phrase “equal parts” should describe a page distribution, not equal storage size.

Approved explanations:

* Divide the pages as evenly as possible
* Choose how many PDF parts you need
* Create a selected number of page-balanced files
* Distribute the document pages across several results

Avoid:

* Same file size
* Identical MB
* Perfectly equal PDFs
* Equal amount of content
* Equal number of words
* Balanced automatically by complexity

A 10-page PDF divided into 3 parts may produce ranges such as 1–4, 5–7, and 8–10, depending on the implemented distribution rule. Public examples must follow the real engine behavior.

---

## Maximum-Pages Accuracy

Maximum-pages splitting is one of PMAS’s clearest PDF-specific benefits.

Safe claims:

* Set a maximum number of pages per PDF
* Break long documents into page-limited files
* Prepare smaller page groups for review, sharing, or submission
* Create consecutive PDF parts based on your selected page limit

Use carefully:

* Each result has exactly the selected number of pages
* Every file stays below a service limit
* Smaller files
* Easier to send

The final part may contain fewer pages.

The generated file size in MB can still vary because page content differs.

Avoid:

* Meet any email attachment limit
* Keep every file under 10 MB
* Compress large PDFs
* Optimize images automatically
* Guarantee upload acceptance

## Cover-Page Workflow Accuracy

Safe claims:

* Add an optional cover page to the result
* Use a title page to identify the merged PDF
* Add the selected cover at the beginning of each split part
* Adjust the cover image using the available controls
* Preview the cover before creating the PDF
* Prepare a report, project, portfolio, or document cover

The cover is a new PDF page.

For merge:

* it is inserted once at the beginning of the merged result when selected

For split:

* it is inserted at the beginning of each generated part when selected

The quality control applies to the cover image only. It must not imply that the original PDF pages are recompressed or rendered at the selected image quality.

Validate before claiming:

* every cover format is supported
* a cover is generated automatically
* text is generated for the cover
* the app designs professional covers
* original document pages are enhanced
* covers are optimized for every printer or viewer
* cover dimensions always match every source page

The cover workflow must be positioned as preparation of the PDF result.

It must not make PMAS look like:

* PDF Cover Maker
* a graphic-design app
* an AI cover generator
* a photo editor
* a document template marketplace

## Output and File-Control Accuracy

Every locale should make the output understandable.

For merge:

**Several source PDFs → one created PDF**

For split:

**One source PDF → several created PDF files**

The listing should make clear that the app produces new files.

Safe claims:

* Save created PDFs
* Open the result in compatible apps
* Share created PDF files
* Find results in My PDFs
* Rename saved results
* Delete saved results
* Keep source PDFs separately
* Create a new PDF result
* Avoid partial output files when an operation fails or is cancelled, when verified

Avoid:

* Open in every PDF reader
* Automatically upload to Google Drive, OneDrive, Dropbox, or another service
* Sync across devices
* Publish the result
* Send directly to a government, school, employer, or signing platform
* Replace the original PDF unless that is explicit behavior
* Back up files to the cloud
* Print directly unless the app contains a verified print action
* Edit the generated PDF after creation unless a separate editor exists

“Open” must mean using the system or a compatible installed application, not reading the PDF inside PMAS unless an internal reader actually exists.

## Preservation and Rewriting Accuracy

PMAS should communicate that it works with real PDF pages, but it must not promise perfect preservation of every advanced PDF feature.

Approved high-level wording:

* Original pages remain PDF pages
* Text, images, and vector content are not intentionally flattened into page screenshots
* Different page sizes and orientations can remain in the result
* PMAS rewrites the document structure to create new PDF files
* Common annotations, links, and bookmarks are retained where supported

Claims requiring caution:

* All forms remain fully interactive
* Every signature remains valid
* Every page label is preserved
* Every nested bookmark action is preserved
* Every internal link works after splitting
* Attachments are copied to every result
* JavaScript actions remain available
* Permissions and encryption remain unchanged

Known limitations that should guide public claims and in-app warnings:

* Rewriting a signed PDF invalidates its existing cryptographic signatures.
* Imported form widgets may remain visible while the global AcroForm structure is not fully reconstructed.
* Page labels may require explicit reconstruction and should not be promised without verification.
* First-level navigable bookmarks may be regenerated, while complex actions or unsupported hierarchies may be omitted.
* URI links and common annotations may be imported, while internal destinations that point outside a generated split part require review.
* Attachments, portfolios, JavaScript, and advanced interactive structures are not safe default preservation claims.

The Play Store listing does not need to expose every implementation warning, but it must avoid contradicting them.

---

## Privacy and Local-Processing Accuracy

Approved high-level trust proof:

* PDF processing happens on your device
* No account is required
* No document uploads are needed for merge or split
* Your PDF content stays under your control
* Files are created locally
* Merge and split processing stays on the device

Avoid:

* 100% offline, if rewarded advertisements or access checks may require internet
* Nothing ever connects to the internet
* No network access
* Completely offline in every mode
* Anonymous cloud processing
* Secure temporary uploads
* Encrypted server conversion

The most accurate default statement is:

**Your PDF content is processed on your device and is not uploaded for merging or splitting.**

This distinguishes file processing from advertising, billing, analytics, or other app services.

Because PDFs often contain contracts, statements, forms, IDs, school records, or work material, privacy can carry more conversion weight than in EMAS. It should still support the main merge/split proposition rather than replace it.

---

## Monetization Accuracy

Monetization must remain secondary.

Approved phrasing when applicable:

* Remove ads with an upgrade option
* Some free creation actions may use a rewarded ad
* Upgrade for an ad-free experience
* If an ad cannot load, the app provides the implemented fallback
* The result workflow remains clear if advertising is unavailable

Avoid:

* Free unlimited merges
* Free unlimited splits
* Always free
* No ads
* Completely offline
* Unlimited processing
* Lifetime access to every future premium feature
* Pro-quality PDF unless a specific output difference exists
* Hiding a required advertisement from the listing when it materially affects the main workflow

The first screenshots must not focus on monetization.

Settings and Remove Ads should not replace proof of merge, split, page control, or output clarity.

No locale may introduce claims about:

* Editing PDF text
* Editing images already inside a PDF
* OCR or scanned-text recognition
* Creating searchable PDFs
* Compressing PDFs
* Reducing PDF size
* Splitting by exact MB size
* Converting Word, Excel, PowerPoint, EPUB, images, or other formats to PDF
* Converting PDF to other formats
* Scanning with the camera
* Repairing damaged PDFs
* Recovering missing pages
* Removing passwords or encryption
* Bypassing document permissions
* Preserving cryptographic signature validity after rewriting
* Applying new digital signatures
* Filling or designing forms
* Redacting confidential information
* Translating PDF content
* Correcting grammar or spelling
* Summarizing documents
* AI-based bookmark generation
* AI-based page classification
* Cloud processing
* Automatic publishing or submission
* Guaranteed exact file sizes
* Guaranteed compatibility with every PDF viewer
* Guaranteed preservation of every annotation, link, form, bookmark, page label, attachment, portfolio, or script
* Uploading directly to a government, school, bank, employer, or cloud service
* Official affiliation with Adobe, Google Drive, Microsoft, Dropbox, or another platform
* Unlimited source files or output pages unless verified

Unsupported claim risk must score **5/5** before publication.

* MERGE OR SPLIT PDFs

# Global Findings

All localized variants must preserve the same actual product identity:

**PDF Merge & Split combines compatible PDF documents into one ordered result and divides a compatible PDF into new files using bookmarks, manual page boundaries, equal page distribution, or a maximum-pages rule.**

The strongest default conversion hierarchy is:

**Merge or split → control document order or page boundaries → preview the result → add an optional cover page → save new PDFs → keep processing local.**

The strongest merge proof is:

**Multiple PDFs shown in a user-selected order, producing one clear result.**

The strongest split proof is:

**One PDF shown with a selected method and an understandable preview of the resulting page ranges.**

The strongest differentiation proof is:

**Existing bookmarks for document structure, manual points for exact control, equal parts for quick distribution, and maximum pages for predictable page groups.**

The strongest preservation proof is:

**Original pages remain PDF pages instead of being intentionally converted into screenshots.**

The strongest output proof is:

**Created PDF files can be saved, opened with compatible apps, shared, renamed, deleted, and found again in My PDFs.**

The strongest trust proof is:

**PDF processing happens on the device. No account is required. PDF content is not uploaded for merging or splitting.**

The largest global conversion risk is making PMAS look like:

* a generic PDF toolkit
* a PDF compressor
* an online converter
* a full PDF editor
* a scanner or OCR app
* a digital-signature tool
* a password utility
* a cloud processing service
* an AI document-analysis tool
* a collection of unrelated PDF features

The largest technical-accuracy risks are:

* promising identical file sizes from equal parts
* confusing maximum pages with maximum MB
* promising bookmark splitting when no bookmarks exist
* promising unlimited input files without practical validation
* promising complete preservation of forms, signatures, page labels, annotations, links, bookmark actions, attachments, portfolios, or scripts
* implying that every PDF can be merged or split successfully
* implying that rewriting leaves digital signatures valid
* implying that cover quality affects the original PDF pages

# Final Conclusion

A localized PDF Merge & Split listing is approved when it:

* communicates the merge and split value immediately
* adapts its conversion angle to the target region
* uses document examples that feel locally relevant
* proves user control over ordering and page boundaries
* explains bookmarks as existing source structure
* distinguishes equal page distribution from equal file size
* distinguishes maximum pages from compression or MB limits
* shows understandable source-to-result relationships
* presents the cover as an optional title page for the created result
* shows new PDF files as the final output
* explains that original pages remain PDF pages without promising perfect preservation of every advanced feature
* supports local-processing trust without replacing the main value
* treats monetization as secondary
* avoids claims outside the real implementation

**Choose merge or split → organize documents or page ranges → preview the output → optionally prepare a cover page → save new PDF files locally.**

The exact order may change by region.
